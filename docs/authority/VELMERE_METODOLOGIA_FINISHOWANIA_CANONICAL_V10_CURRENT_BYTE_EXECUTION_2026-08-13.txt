- high TVL automatically upgrades severity
- low CVSS automatically suppresses protocol-specific business-logic loss
- one scalar silently aliases severity + probability + impact
- stale exploit intelligence remains current

M22 — DIAGNOSTIC EQUIVALENCE / RUNNER IDENTITY / CONFLICT ADJUDICATION

Cel:
Nie dopuścić, aby dwa różne narzędzia lub konfiguracje wydały sprzeczne receipts pod tą samą nazwą „TypeScript PASS/FAIL”.

Zasady obowiązkowe:
1. Każdy diagnostic/typecheck/build receipt musi wiązać co najmniej:
   - executable path i SHA-256,
   - Node/npm/TypeScript version,
   - package.json i lockfile SHA-256,
   - tsconfig path i SHA-256,
   - dokładną komendę, cwd, zmienne środowiskowe istotne dla wyniku,
   - source aggregate SHA-256 albo manifest wejściowy,
   - klasę kredytu: SYNTAX_ONLY / TRANSPILE_DIAGNOSTIC / PROJECT_TYPECHECK / PRODUCTION_BUILD.
2. `transpileModule` albo `node --check` nie są project typecheckiem i nie mogą zastępować buildu.
3. Zewnętrzny/globalny TypeScript może dać wyłącznie `DIAGNOSTIC_ONLY`, dopóki project-local dependency closure nie jest udowodnione.
4. Jeżeli dwa runy są sprzeczne, nie wolno wybierać wygodniejszego wyniku ani uśredniać. Stan to `CONFLICTED_DIAGNOSTIC` do czasu adjudication.
5. Adjudication wymaga powtórzenia na tym samym frozen source, project-local exact toolchainie i właściwym tsconfig. Każda różnica wejścia musi być jawna.
6. Brakujące ambient types/dependencies odróżnia się od błędu składni i od błędu logiki produktu.
7. Wynik sprzeczny lub niepełny nie blokuje zapisu WIP SOURCE, ale blokuje production/build credit.
8. Mutation control musi udowodnić, że runner wykrywa celowo wprowadzony błąd składni oraz błąd typu w zakresie, do którego rości sobie credit.

PASS M22 oznacza, że wszystkie aktualnie cytowane diagnostics mają jednoznaczną tożsamość, klasę kredytu i brak nierozstrzygniętego konfliktu.

M22-A — P32 CURRENT-BYTE EXECUTION CLASSIFICATION / HISTORICAL DRIFT / EXTERNAL QA ASSET BOUNDARY
======================================================================

Cel:
Rozdzielić faktyczne current-byte wykonanie od błędu runnera, historycznego linkage, finalnego holdoutu i customer-value closure.

Zasady obowiązkowe:
1. Bezpośrednie uruchomienie pliku `.ts` przez runner, który nie obsługuje deklarowanego loadera/transpilacji, nie jest automatycznie product/source FAIL. Najpierw trzeba uruchomić ten sam test przez zadeklarowany loader albo project-local exact runner i zachować oba receipts.
2. Historyczna polityka, manifest lub source-summary z nieaktualnym hashem nie może być cicho przepisany. Dopuszczalne jest current-byte revalidation, jeżeli:
   - historyczny plik pozostaje bez zmian,
   - wszystkie zmienione input hashes są jawnie wymienione,
   - runtime jest ponownie wykonany na aktualnych bajtach,
   - credit class wyraźnie mówi, że historyczny release linkage nie został promowany.
3. Exact hash-bound asset potrzebny wyłącznie do QA może być odzyskany z historycznego evidence/MATERIALS i użyty jako zewnętrzny input, jeżeli:
   - byte length i SHA-256 zgadzają się z frozen contract,
   - provenance odzyskania jest zapisane,
   - asset nie jest kopiowany do SOURCE, jeżeli kontrakt tego zabrania,
   - asset nie jest udostępniany użytkownikowi jako osobny artefakt.
4. `EXECUTED_INTERNAL_FIXTURE_REGRESSION` oznacza wyłącznie, że profil ma current-byte lokalne wykonanie na syntetycznym/fixture denominatorze. Nie zamyka:
   - final holdout,
   - ground-truth quality,
   - novelty/duplication,
   - decision-change,
   - customer value/WTP/refund risk,
   - provider/data rights,
   - paid tier, LIVE, sale albo production build.
5. PDF generation + parser/raster QA nie jest Browser execution. Browser profile pozostaje `BLOCKED_BROWSER_EXECUTION_NOT_RUN`, dopóki rzeczywisty customer/browser journey nie zostanie wykonany i zarchiwizowany.
6. Profile definitions i profile execution receipts są osobnymi artefaktami. Wykonanie nie może nadpisywać frozen definition; musi wskazywać `definitionSha256`.
7. Każdy profile-execution manifest musi mieć mutation controls wykrywające co najmniej:
   - fałszywe podniesienie Browser do EXECUTED,
   - fałszywe zamrożenie final holdoutu,
   - fałszywe customer-value closure,
   - shrink denominatora profili.
8. Structural/offline readiness jest metryką diagnostyczną. Nigdy nie jest samodzielnym dowodem ceny ani wartości płatnego tieru.

- każdy wykonany profil ma current-byte receipt związany z frozen definition,
- Browser/PDF i fixture/final-holdout pozostają niealiasowane,
- historyczny drift jest jawny,
