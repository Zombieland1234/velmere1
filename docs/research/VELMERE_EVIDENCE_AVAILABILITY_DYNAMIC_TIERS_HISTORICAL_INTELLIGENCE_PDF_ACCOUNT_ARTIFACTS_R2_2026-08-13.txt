======================================================================
0. CEL
======================================================================

Pomysł polega na tym, aby Velmère NIE zachowywało się jak zwykły sklep, w którym
Basic / Pro / Advanced są zawsze aktywne niezależnie od jakości danych.

Zamiast tego każdy produkt i każdy tier powinien być dynamicznie dostępny wyłącznie
wtedy, gdy system posiada wystarczające, odpowiednio świeże, zgodne, legalnie
używalne i technicznie osiągalne evidence do uczciwego dostarczenia obiecanej wartości.

Najważniejsza zasada:

NIE:
"Tier istnieje w cenniku => można go kupić."

TYLKO:
"Tier istnieje w cenniku => system robi preflight => jeśli evidence spełnia kontrakt
tego tieru => zakup zostaje aktywowany."

Jeżeli warunki nie są spełnione:
- zakup zostaje zablokowany;
- klient dostaje uczciwy powód;
- system może zaproponować niższy dostępny tier;
- system może zaoferować Historical Snapshot;
- system może pokazać ostatni moment pełnej dostępności;
- system może pokazać następny zaplanowany re-check;
- system NIE wymyśla ETA, jeśli go nie zna.

To ma być przewaga jakościowa Velmère:
system potrafi odmówić sprzedaży produktu, którego nie może w danej chwili
uczciwie dostarczyć na wymaganym poziomie.

1. GŁÓWNY MODUŁ — VELMÈRE EVIDENCE AVAILABILITY ENGINE
======================================================================

Proponowana nazwa wewnętrzna:
Velmère Evidence Availability Engine (VEAE)

Odpowiada za:
1. sprawdzenie jakości i dostępności wejść;
2. sprawdzenie freshness;
3. sprawdzenie provider conflicts;
4. sprawdzenie required evidence;
5. sprawdzenie praw/licencji;
6. sprawdzenie runtime reachability;
7. sprawdzenie health wymaganych usług;
8. sprawdzenie tier-specific requirements;
9. wyznaczenie najwyższego uczciwie dostępnego tieru;
10. sterowanie checkoutem;
11. sterowanie customer-facing state;
12. wskazanie Historical Snapshot, jeżeli current nie jest dostępne;
13. zlecenie następnego re-checku;
14. przechowywanie historii availability;
15. generowanie evidence receipt decyzji AVAILABLE / UNAVAILABLE.

VEAE NIE powinien opierać swojej końcowej decyzji wyłącznie na odpowiedzi AI.

AI/VLM Brain może:
- wykrywać brakujące evidence;
- klasyfikować kontekst;
- proponować wymagane dodatkowe kontrole;
- opisywać klientowi ograniczenie;
- szukać sprzeczności.

Ale ostateczne saleEligible=true/false powinno wynikać z deterministycznego
policy/eligibility engine.


======================================================================
2. CUSTOMER-FACING AVAILABILITY STATES
======================================================================

Proponowane stany:

AVAILABLE
Produkt/tier posiada wszystkie wymagane krytyczne evidence. Zakup aktywny.

AVAILABLE_WITH_LIMITATIONS
Produkt jest dostępny, ale istnieją jawne niekrytyczne ograniczenia.
Zakup może być aktywny tylko, jeśli kontrakt tieru dopuszcza ten stan.

WAITING_FOR_FRESH_EVIDENCE
Wymagane źródło istnieje, ale observation jest zbyt stary albo oczekujemy
na nową weryfikację.

HISTORICAL_ONLY
Nie można uczciwie dostarczyć current intelligence, ale istnieje prawidłowo
oznaczony snapshot historyczny.

TEMPORARILY_UNAVAILABLE
Produkt był osiągalny, ale obecnie krytyczna zależność nie spełnia wymagań.

UNSUPPORTED
Ten asset/contract/use case nie jest obsługiwany przez dany tier.

CONFLICTED
Krytyczne źródła przedstawiają materialnie sprzeczne informacje i polityka
tieru nie pozwala jeszcze na bezpieczną adjudykację.

RIGHTS_BLOCKED
Dane są technicznie osiągalne, ale nie ma potwierdzonych praw do ich użycia
w danym customer/commercial context.

SYSTEM_DEGRADED
Dane są wystarczające, ale runtime/operational health nie pozwala bezpiecznie
dostarczyć produktu.

W customer UI można użyć prostszych komunikatów, bez ujawniania wewnętrznej topologii.

4. DYNAMICZNA DOSTĘPNOŚĆ BASIC / PRO / ADVANCED
======================================================================

BASIC
Najbardziej odporny i szeroko dostępny tier.
Może działać przy częściowej dostępności danych, jeżeli:
- critical minimum evidence istnieje;
- brakujące dane są jawnie oznaczone;
- brakujące dane nie powodują fałszywego wniosku;
- Basic nadal daje rzeczywistą wartość.

Basic NIE może być celowo osłabiany, żeby wymusić Pro.

PRO
Powinien wymagać:
- dodatkowych evidence families;
- lepszego cross-checku;
- większej freshness krytycznych pól;
- głębszego reasoning;
- dodatkowych derivations;
- historii tam, gdzie jest wartością;
- większej traceability;
- dodatkowych testów.

Jeżeli krytyczna warstwa Pro jest niedostępna:
Pro = TEMPORARILY_UNAVAILABLE
Basic może nadal działać.

ADVANCED
Najostrzejszy gate.
Dla Audit może wymagać m.in.:
- source;
- exact compiler/settings;
- deployed runtime identity, jeżeli scope tego wymaga;
- proxy/admin mapping;
- spec/trust model;
- dynamic testing;
- fuzz/invariants;
- business-logic inputs;
- evidence dla multi-lane AI review;
- contradiction/adjudication completion;
- evidence-pack completeness.

Jeżeli krytyczny warunek odpada:
Advanced purchase = disabled.

Klient widzi np.:
Advanced temporarily unavailable
Missing: verified deployment identity + protocol specification
Pro available now

11. WHAT CHANGED? — VLM BRAIN DELTA ANALYSIS
======================================================================

VLM Brain dostaje dwa zatwierdzone evidence snapshots i analizuje wyłącznie delta.

Przykład:
Between 03:20 and 04:10:
- liquidity: -18.2%
- holder concentration: +4.1 pp
- proxy implementation: unchanged
- admin permissions: unchanged
- oracle freshness: degraded
- provider disagreement: increased
- two large transfers observed
- no evidence that transfers were sales
- risk priority: MODERATE -> ELEVATED

Reason for priority change:
liquidity deterioration + provider disagreement

Missing:
current second-provider confirmation

To może mieć większą wartość niż sama tabela aktualnych liczb.

22. REFUND / DELIVERY SAFETY — RACE CONDITION
======================================================================

Eligibility może zmienić się między preflightem a payment confirmation.

Przykład:
04:00 preflight = Pro available
04:01 payment
04:01:05 provider becomes critically stale

Policy A:
jeżeli analiza nie rozpoczęta -> block execution + cancellation/refund.

Policy B:
jeżeli degraded Pro jest dozwolony -> wymagana jawna zgoda klienta.

Nigdy:
silent downgrade albo dostarczenie gorszego produktu po pełnej cenie.

Powinien istnieć drugi server-side eligibility gate przed entitlement/delivery.

68. SECURE DOWNLOAD CONTRACT
======================================================================

Rekomendacja:

1. Użytkownik klika download.
2. Server sprawdza session/account/tenant/artifact/retention/revocation.
3. Server wydaje krótko ważny download token lub streamuje bezpośrednio.
4. Token jest związany z:
   - artifactId;
   - accountId;
   - expiry;
   - action=download;
   - optional single use.
5. Object storage nie jest publiczny.
6. Każdy download jest logowany bez ujawniania treści.

Przykładowa ważność signed URL:
5–15 minut jako hipoteza techniczna.

Nie traktować tej liczby jako wymogu prawnego.
